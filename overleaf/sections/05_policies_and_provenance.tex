\section{Policy Language and Provenance Tracking}
\label{sec:policies}

\subsection{Policy Language}

\sys{} policies are expressed in YAML for accessibility to operators who are not security specialists; integration with formal policy languages such as Rego or Cedar is future work. This section details the constructs.

\paragraph{Risk Tiers.}
Tools are categorized by inherent risk: LOW (read-only, e.g., \texttt{fs.read}), MEDIUM (create/modify, e.g., \texttt{fs.write}), HIGH (destructive/exfiltrating, e.g., \texttt{fs.delete}, \texttt{email.send}), and CRITICAL (system-level, e.g., \texttt{device.reboot}).

\paragraph{Policy Rules.}
Each rule specifies a name, applicable tools, conditions, and an action (ALLOW, DENY, or CONFIRM). Conditions include: provenance trust (trusted/untrusted source), scope constraints (path prefixes, allowlists), temporal constraints (time-of-day), rate limits, and evidence requirements (structured justification). Conditions combine with boolean AND logic. Example:

\begin{verbatim}
rules:
  - name: "Allow benign file reads"
    tools: ["fs.read"]
    conditions: {path_prefix: "/home/user/",
                 provenance_trust: "trusted"}
    action: ALLOW
  - name: "Confirm untrusted deletes"
    tools: ["fs.delete"]
    conditions: {provenance_trust: "untrusted"}
    action: REQUIRE_CONFIRMATION
\end{verbatim}

\paragraph{Evaluation Semantics.}
Rules are evaluated top-to-bottom; the first matching rule determines the action (\emph{first-match semantics}). First-match evaluation requires careful rule ordering---a broad ALLOW rule placed before a narrow DENY rule can inadvertently shadow the denial. Our policy templates ship with a linting tool that detects shadowed rules. If no rule matches, defaults apply: HIGH/CRITICAL tools require confirmation, while LOW/MEDIUM tools are allowed. The fail-safe guarantee is conservative trust labeling (unknown provenance $\to$ UNTRUSTED), while the final ALLOW/DENY/CONFIRM outcome remains policy-dependent.

\paragraph{Intuition.}
The provenance graph tracks the origin of every piece of data the agent processes. It has two kinds of starting nodes with fixed labels: \emph{user commands} are always TRUSTED, and \emph{external data} (device names, file contents, API responses) is always UNTRUSTED. Every other node inherits its label by looking at all its ancestors---if \emph{any} ancestor is UNTRUSTED, the node is UNTRUSTED. Trust can only be restored by explicit user confirmation. When a tool call is proposed, the proxy checks whether its arguments trace back to untrusted sources; if so, the policy can deny or escalate.

\paragraph{Formal Provenance Model.}
\sys{} maintains a DAG $G = (V, E, T, \tau)$ adapted from W3C PROV-DM~\cite{prov-dm} (Fig.~\ref{fig:provenance-graph}, Table~\ref{tab:node-types}): $V$ are typed provenance nodes (PROV-DM entities); $E$ are directed \texttt{wasDerivedFrom} edges; $T: V \to \mathcal{L}$ assigns trust labels from the two-element lattice $\mathcal{L} = \{\top, \bot\}$ with $\bot \sqsubseteq \top$; and $\tau: V \to \mathbb{N}$ records creation timestamps. LLM-generated content lacking traceable source nodes defaults to $\bot$ (conservative); only nodes with at least one explicit trusted ancestor \emph{and} no untrusted ancestors receive $\top$. TOOL\_CALL trust reflects \emph{origin of intent} (who authorized the action), while TOOL\_RESULT trust reflects \emph{origin of content} (where data came from)---these are independent: a trusted command may trigger a call whose result is untrusted. This captures \emph{why-provenance}~\cite{buneman2001provenance} at the tool-call boundary; \emph{how-provenance} (the LLM's internal transformation) is not tracked because the model is opaque.

\paragraph{Trust Propagation.}
Trust labels propagate via the lattice meet ($\sqcap$) over ancestors:
\begin{equation}
\label{eq:trust-propagation}
T(v) = \sqcap_{u \in \text{ancestors}(v)} T(u) = \begin{cases} \top & \text{if } \forall u \in \text{ancestors}(v) : T(u) = \top \\ \bot & \text{otherwise} \end{cases}
\end{equation}
This conservative propagation ensures monotonicity: once a node acquires the $\bot$ (UNTRUSTED) label through any ancestor, no subsequent derivation can restore $\top$ without explicit user declassification (a controlled \emph{downgrading} operation~\cite{difc-survey}).

The two-element lattice establishes three formal properties by construction (detailed in Appendix~\ref{sec:appendix-proofs}): \emph{Propagation Soundness} ($T(v)=\top \Rightarrow$ all ancestors are $\top$), \emph{Taint Monotonicity} ($\bot$ propagates transitively), and \emph{Declassification Control} ($\bot \to \top$ requires authenticated user confirmation). Multi-level trust is future work.

\paragraph{Provenance Queries.}
The policy engine queries the graph via BFS in $O(|V|+|E|)$ (with $|V|<100$ per session): \texttt{get\_sources(c)} returns source nodes (why-provenance), \texttt{is\_trusted(c)} computes the ancestor meet, and \texttt{get\_untrusted\_sources(c)} returns $\bot$-labeled sources for user-facing explanations.

\paragraph{Provenance Resolution Pipeline.}
Provenance resolution determines whether a tool-call argument traces to untrusted content. \sys{} uses a three-stage pipeline:
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Substring match} (fast path): Check if the argument appears verbatim in any TOOL\_RESULT node content. Handles literal arguments (file paths, email addresses, device IDs) with $O(n)$ scan.
  \item \textbf{Embedding similarity}: Compute cosine similarity between the argument's sentence embedding (all-MiniLM-L6-v2, 384-d) and all TOOL\_RESULT node embeddings. Matches above threshold $\theta = 0.45$ link the argument to the untrusted source, handling paraphrased content. Overhead: $<$5\,ms per comparison, no GPU required.
  \item \textbf{Conservative default}: If neither method resolves provenance, the argument is labeled UNTRUSTED (fail-safe).
\end{enumerate}
The threshold $\theta = 0.45$ was selected via 5-fold cross-validation on 20 held-out paraphrase pairs, optimizing for $F_1$ score. The pipeline achieves 100\% provenance recall across 96 paraphrase tests (Section~\ref{subsec:paraphrase}), vs.\ 40.6\% for substring alone.

Sensitivity analysis confirms stability across $\theta \in [0.35, 0.55]$ (Table~\ref{tab:threshold_sensitivity}, Appendix~\ref{sec:appendix-threshold}); the conservative Stage-3 default is a safety net when $\theta$ misclassifies.
