\section{Discussion}
\label{sec:discussion}

\subsection{Data Provenance as a Security Primitive}

Our evaluation reveals \emph{when} provenance matters most. On the 200-scenario benchmark, deterministic dangerous-action rules suffice for most attacks: Policy-Only achieves 1.88\% ASR-IA because the attack tools (delete, unlock, extreme temperature) are syntactically identifiable. Provenance adds marginal security here but provides audit context and confirmation gating. The decisive evidence comes from InjecAgent, where Policy-Only degrades to 22.67\% ASR---no better than No Defense---while \sys{} achieves 4.12\%. The difference is structural: InjecAgent's attacker tools (\texttt{GmailSendEmail}, \texttt{BankManagerTransferFunds}) are legitimate tools invoked with attacker-derived arguments. No syntactic rule can distinguish these calls from benign ones. Provenance provides the missing \emph{context}---the data lineage that reveals whether an argument originated from a trusted user command or an attacker-controlled tool response---enabling fine-grained security decisions at the tool-call boundary that are impossible without lineage tracking.

\subsection{Limitations}

\paragraph{Policy Engineering Burden.}
Although \sys{}'s declarative YAML policies are more accessible than code-level security rules, crafting policies that capture legitimate use patterns without creating security gaps requires domain expertise. The false positives in our evaluation highlight the need for ongoing policy refinement. Notably, all false positives stem from overly conservative \emph{policy rules} (e.g., numeric range checks on device parameters and sensitive-path pattern matching), not from provenance misclassification---the provenance DAG correctly identifies these benign arguments as trusted, but the policy engine still restricts them. This distinction is important: argument validation in the enforcement proxy now \emph{informs} the policy decision (marking arguments as untrusted) rather than bypassing it, so false positives are always traceable to specific, auditable policy rules. Mitigations include: (1)~policy templates for common deployment configurations; (2)~adaptive policies that learn from user feedback; (3)~policy testing frameworks that evaluate proposed rules against the benchmark before deployment.

\paragraph{Policy-Only Comparison Baseline.}
Policy-Only is configured identically to \sys{} except that provenance resolution is disabled (\texttt{has\_untrusted\_args = false}), so only deterministic dangerous-action rules (delete, unlock, extreme temperature) and risk-tier defaults apply. On the 200-scenario benchmark (Table~\ref{tab:baseline_comparison}), Policy-Only achieves 1.88\% ASR-IA with 97.50\% TSR---performing well because the benchmark's attack tools are syntactically dangerous. The benchmark ASR-IA difference (1.09\% vs.\ 1.88\%) is significant before Bonferroni correction ($p = 0.013$, Fisher exact) but not after adjustment for six pairwise comparisons ($p_{\text{adj}} = 0.076$; Cohen's $h = 0.07$, negligible effect). This is expected: when attack tools are syntactically dangerous, provenance adds marginal security. The decisive evidence is InjecAgent (Section~\ref{subsec:injecagent}), where the difference is both large and significant ($p_{\text{adj}} < 0.001$, $h = 0.52$).

The InjecAgent results (Table~\ref{tab:injecagent}) expose Policy-Only's fundamental limitation: 22.67\% ASR, no better than No Defense (20.83\%). The failure is not a matter of policy tuning---it is architectural. InjecAgent's attacker tools (\texttt{GmailSendEmail}, \texttt{BankManagerTransferFunds}, \texttt{AugustSmartLockGrantGuestAccess}) are ordinary tools that do not appear in any dangerous-action list. Without provenance, every call to these tools looks legitimate, and the policy engine has no basis for denial. \sys{} reduces ASR to 4.12\% because the provenance DAG traces each argument to the untrusted tool response that delivered the injection payload, giving the policy engine the evidence it needs to block the call.

\paragraph{Why Not ``Taint Everything''?}
An alternative design treats \emph{all} external tool results as untrusted regardless of actual lineage (\texttt{has\_untrusted\_args = true} for every call involving tool-result data). Our Taint-Everything ablation (Tables~\ref{tab:baseline_comparison} and~\ref{tab:taint_everything}) quantifies this tradeoff: blanket tainting achieves \textbf{0.00\%} ASR-IA but collapses TSR to \textbf{9.00\%}---a 90.75\% false positive rate that makes the agent non-functional for its intended purpose. \sys{}'s three-stage provenance resolution avoids this by distinguishing the specific arguments that trace to attacker-controlled sources from those that do not. The result is selective enforcement: the same tool can be allowed or denied depending on \emph{where its arguments came from}, achieving 1.09\% ASR-IA with 95\% TSR. The concrete tradeoff is 9$\times$ better usability at a marginal security cost of $<$1.1 percentage points of ASR---a compelling operating point for production deployments where agent functionality must be preserved.

\paragraph{Provenance Granularity.}
Provenance is tracked at argument level via the lattice meet. This can be overly conservative when benign and malicious content co-locate in the same tool result. Fine-grained sub-argument provenance would improve precision but significantly increase complexity. Embedding-enhanced provenance (RQ6) addresses the orthogonal paraphrase problem, achieving 100\% recall on NL arguments.

\paragraph{Semantic Understanding.}
Policies check paths, tool names, and provenance labels but cannot reason about \emph{intent}. Integrating a secondary LLM for intent analysis could improve precision but introduces latency, a new attack surface, and non-deterministic behavior that undermines \sys{}'s policy determinism property.

\paragraph{Taint Explosion.}
Conservative propagation risks labeling the entire system state as untrusted in long conversations. Our benchmark's high TSR indicates this is manageable for typical workflows (median 3--5 tool calls), but production agents executing 10--50+ calls per session would face increased confirmation burden. Mitigations include sanitization primitives (\texttt{declassify()}), periodic taint reset at session boundaries, and scope-limited propagation.

\subsection{Design Choice: Binary Trust Lattice}

A natural question is whether the binary $\{\top, \bot\}$ lattice is too coarse---would a richer lattice (e.g., TRUSTED, PARTIALLY\_TRUSTED, UNTRUSTED, or per-source labels) improve precision? We argue the two-element lattice is the right design point for three reasons. First, in our threat model, external content is either attacker-controllable or it is not---there is no meaningful intermediate trust level for data that transits through IoT APIs, shared calendars, or file contents. Second, a richer lattice introduces policy complexity (how should partially-trusted arguments be handled?) without clear security benefit: our evaluation shows the binary lattice already achieves high TSR with low false positives, all of which stem from policy rules rather than trust granularity. Third, the meet operator over a two-element lattice is maximally conservative---any richer lattice would require application-specific ordering that reduces generality. Extending to multi-level trust for domains with authenticated external sources (e.g., digitally-signed sensor data) is a natural direction for future work.

\subsection{Analysis of Residual Bypasses}

Residual attacks fall into three modes. \textbf{Encoding obfuscation} (2.78\% category ASR): encoded payloads evade argument validation despite correct provenance tracking. Our canonicalization preprocessor blocks the six most common patterns, but novel encoding variants remain the primary residual weakness. \textbf{Indirect chaining}: privilege escalation and confused deputy attacks propagate through legitimate intermediate steps that dilute the provenance signal; mitigation requires tighter scope constraints. \textbf{Confidentiality exfiltration}: ASR-IA captures integrity/availability but not confidentiality. The InjecAgent DS results (8.6\% ASR-C vs.\ 0\% for Direct Harm) confirm that data exfiltration through MEDIUM-risk channels (email, messaging) is the primary residual gap~\cite{greshake2023not}. Mitigations include content-length restrictions and reclassifying data-export tools as HIGH risk.

\subsection{Model Selection and Generalizability}

Our evaluation spans five models across four vendor families (3B--122B parameters). The cross-model results (Table~\ref{tab:crossmodel}) demonstrate that provenance-based defense \emph{compensates} for model-level differences: more compliant models generate more tool calls, but the boundary layer blocks a proportionally larger share. This complementary behavior means \sys{}'s effectiveness does not depend on the agent model's built-in safety. Even with safety training, the majority of attack prompts produce at least one tool call---demonstrating that model-level safety alone is insufficient~\cite{bing-sydney,greshake2023not}.

\subsection{Evaluation Limitations}

We acknowledge several limitations:

\paragraph{Self-Constructed Benchmark.}
Our 200-scenario benchmark is author-crafted, enabling precise control but introducing potential bias. The InjecAgent evaluation partially addresses this; further validation on AgentDojo~\cite{agentdojo2024} is future work.

\paragraph{Model Scale.}
Our 3B--122B evaluation confirms scalability (0\% ASR-IA on 122B), but proprietary models (GPT-4, Claude) with different tool-calling conventions remain untested.

\paragraph{Repetition Design.}
Each of the five repetitions uses a unique cryptographic seed derived from \texttt{SHA-256(scenario\_id $\|$ system $\|$ model $\|$ rep)}, ensuring trial-level independence. Temperature varies as $T=0.0$ (greedy) for rep~1 and $T \in \{0.10, 0.15, 0.20, 0.20\}$ for reps~2--5 (reps~4 and 5 share $T=0.20$ but use distinct seeds). All reported confidence intervals are 95\% Wilson-score intervals computed over pooled trials; they depend only on the observed proportion and trial count, not on rep-to-rep temperature variation. The consistent per-rep ASR (1.09\% across all five reps) reflects the structural stability of boundary enforcement rather than insufficient temperature diversity.

\paragraph{User Study.}
Our TSR measures system-level usability. We do not evaluate confirmation fatigue or user comprehension of provenance explanations---a user study is essential future work.

\subsection{Generalization and Ethics}

While evaluated on IoT, \sys{}'s architecture generalizes to any domain with mixed-trust tool inputs: enterprise assistants (data-loss prevention), healthcare agents (provenance-verified suggestions), web browsing agents (source-reputation trust), and code generation (user code vs.\ third-party documentation). Domain adaptation requires tool registries with risk tiers, trust labels for input sources, and YAML policies.

All experiments use simulated tool environments with no real-world side effects. Attack payloads are necessary for measuring defense effectiveness but are never executed against real infrastructure. All documented attack categories are already well-known~\cite{greshake2023not,injecagent2024,owasp-llm2025}. The framework, benchmark, and policy templates will be released as open-source software upon acceptance.
