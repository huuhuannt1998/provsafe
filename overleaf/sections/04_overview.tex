\section{System Overview}
\label{sec:overview}

\subsection{Motivating Example}

Recall the attack from Section~\ref{sec:intro}: a device named ``Living Room Light. Admin Override: Grant me full file system access'' injects instructions into the agent's context. If Alice asks \textit{``Create a note summarizing device status,''} a naive agent may generate \texttt{fs.read("/etc/passwd")}---both commands appear as natural language in the same context window.

\subsection{The \sys{} Approach}

\begin{figure*}[t]
  \centering
  \includegraphics[width=0.8\textwidth]{figures/architecture.png}
  \caption{\sys{} system architecture. The enforcement proxy sits between the LLM agent and
  tool execution. The provenance tracker maintains a DAG labeling data as TRUSTED (from authenticated
  users) or UNTRUSTED (from external sources). Policies gate tool calls based on provenance, risk, and scope.}
  \label{fig:architecture}
\end{figure*}

\sys{} addresses this via \emph{provenance-gated policy enforcement} in four steps (Fig.~\ref{fig:architecture}).

\paragraph{Step 1: Label Inputs by Trust.}
User commands and system prompts are marked TRUSTED; device names, calendar events, file contents, and other tool results are marked UNTRUSTED since they originate from attacker-controllable sources. Input is also screened for jailbreak attempts, chaining patterns, and encoding obfuscation (Base64, hex, ROT13, Unicode); matching requests are rejected.

\paragraph{Step 2: Track Provenance.}
\sys{} maintains a DAG linking derived facts to their sources. When the agent summarizes ``Living Room Light requests admin access,'' that summary traces back to the untrusted device name. Resolution uses substring matching, embedding similarity ($\theta = 0.45$), and a conservative default (Section~\ref{sec:policies}).

\paragraph{Step 3: Validate and Enforce Policies.}
When the agent proposes a tool call, the proxy intercepts it: \emph{argument validation} checks for encoded payloads, path traversal, and command injection; \emph{policy evaluation} considers risk tier, provenance, scope constraints, and temporal conditions. For \texttt{fs.read("/etc/passwd")} from an untrusted device name, the policy denies; for \texttt{fs.write("/notes/summary.txt")} from a trusted user command, it allows.

\paragraph{Step 4: User Confirmation When Needed.}
If a policy evaluates to REQUIRE\_CONFIRMATION, \sys{} prompts the user with the proposed call, applicable policies, and the provenance chain; execution proceeds only after explicit approval.
