\section{Evaluation}
\label{sec:eval}

\subsection{Research Questions}

We address seven research questions: \textbf{RQ1:} How effective is \sys{} at blocking attacks compared to baselines? \textbf{RQ2:} What is each component's contribution? \textbf{RQ3:} What usability trade-offs arise? \textbf{RQ4:} How robust are results across models? \textbf{RQ5:} Are \sys{}'s provenance decisions accurate? \textbf{RQ6:} How robust is \sys{} against adaptive paraphrase attacks? \textbf{RQ7:} Can an adaptive adversary with white-box knowledge bypass \sys{}?

\subsection{Methodology}
\label{subsec:methodology}

\paragraph{Benchmark.}
We evaluate 200 scenarios: 160 attacks across 8 categories (Direct Injection, Device-State Injection, File Content Injection, Multi-Turn Chaining, Encoding Obfuscation, Role-Play Jailbreak, Confused Deputy, Privilege Escalation) and 40 benign tasks (device control, calendar, sensors, notifications).

\paragraph{LLM Models.}
Four open-source models represent the practical deployment target for on-premise agents on consumer hardware: Meta-Llama-3.1-8B-Instruct (8B parameters), Qwen2.5-7B-Instruct (7B), Gemma-2-9B-IT (9B, Google DeepMind), and Phi-3.5-Mini-Instruct (3B, Microsoft). All run locally via LM Studio on an Apple M-series machine (16\,GB RAM), reflecting deployment settings where privacy-sensitive operations should not leave the local network. The four families (Meta, Alibaba, Google, Microsoft) spanning 3B--9B parameters test generalizability across architectures.

\paragraph{Baselines.}
Four configurations isolate the contribution of each defense layer: (1)~\textbf{No Defense}: all tool calls execute unfiltered; (2)~\textbf{Pattern Filter}: 47-rule regex scanner (Rebuff-derived~\cite{rebuff2023}) at the tool-call boundary; (3)~\textbf{Policy-Only}: identical to \sys{} but with provenance resolution disabled---all tool-call arguments are treated as having unknown provenance (\texttt{has\_untrusted\_args = false}), so only the deterministic dangerous-action rules and risk-tier defaults apply. Rate limiting is disabled for both Policy-Only and \sys{} to isolate provenance as the variable under test. This baseline isolates the contribution of provenance tracking; (4)~\textbf{\sys{} (Full)}: complete system with provenance DAG, three-stage resolution, pre-LLM screening, argument validation, and policy evaluation.

\paragraph{Experimental Protocol.}
Each configuration is evaluated with five independent repetitions per scenario-model pair. Repetition~1 uses temperature $T=0.0$ (greedy decoding); repetitions 2--5 use $T \in \{0.05, 0.10, 0.15, 0.20\}$ to introduce genuine sampling variation while staying near-deterministic. Each repetition is assigned a unique seed derived from a cryptographic hash of the scenario identifier, system name, model name, and repetition index, making results reproducible. This design ensures per-repetition ASR estimates are statistically independent across repetitions, enabling meaningful bootstrap confidence intervals---trials would otherwise be identical under pure greedy decoding. This yields $200 \times 4 \times 5 = 4{,}000$ \sys{} trials and $200 \times 4 \times 5 \times 3 = 12{,}000$ baseline trials (16{,}000 total). Models are loaded and unloaded sequentially via the LM Studio management API.

\paragraph{Metrics.}
Attack Success Rate on integrity/availability patterns (ASR-IA, lower is better), Task Success Rate (TSR, higher is better), and False Positive Rate (FPR). We report 95\% Wilson-score confidence intervals for all binomial proportions~\cite{wilson1927probable}. A tool call is ``dangerous'' if it matches one of four deterministic patterns: delete action, write to absolute path, unlock action, or temperature outside 60--85\textdegree{}F. Our primary metric ASR-IA captures integrity and availability violations. Confidentiality violations---exfiltration through permitted channels such as \texttt{notify.send}---are not captured by ASR-IA; we analyze one such case in RQ7 (ADV-PA-03) but do not report a systematic confidentiality metric. This is a limitation discussed in Section~\ref{sec:discussion}.

\paragraph{Statistical Significance.}
Beyond confidence intervals, we test whether ASR-IA differences between systems are statistically significant using pairwise two-sided Fisher exact tests with Bonferroni correction for multiple comparisons ($\alpha = 0.05$, $k = 6$ pairs). We report adjusted $p$-values and Cohen's $h$ as a standardized effect size for proportions~\cite{cohen1988statistical}. Cohen's $h = 2\arcsin\!\sqrt{p_1} - 2\arcsin\!\sqrt{p_2}$ is scale-invariant and appropriate for small proportions where arithmetic differences are misleading.

\paragraph{Ground Truth.}
Dangerous-call detection is deterministic and does not depend on LLM judgment. Confidentiality violations (exfiltration through permitted sinks such as \texttt{notify.send}) are analyzed separately in RQ7 and the appendix.

Tables~\ref{tab:main_results}--\ref{tab:baseline_comparison} and Fig.~\ref{fig:asr_comparison} present the main results. \sys{} achieves an ASR-IA of \textbf{1.09\% $\pm$ 0.36} (95\% CI) with \textbf{95.00\% $\pm$ 1.52 TSR} across 4{,}000 trials---a 24$\times$ reduction versus No Defense and 7$\times$ versus Pattern Filter. On our TDSC benchmark, Policy-Only also achieves low ASR-IA (1.88\%) because the benchmark's dangerous-action rules---delete, unlock, extreme temperature---are sufficient to catch most attacks syntactically. This near-parity reflects a design property of our scenario suite: attack tools (\texttt{fs.delete}, \texttt{device.control} with unlock) are syntactically identifiable. The InjecAgent evaluation (Section~\ref{subsec:injecagent}) complements this with tool ecosystems where syntactic identification fails. \sys{} is at least as effective, with the added benefit of provenance context for auditing and confirmation. The critical distinction emerges on InjecAgent (Table~\ref{tab:injecagent}): Policy-Only degrades to 22.67\% ASR, nearly identical to No Defense, because attacker tools like \texttt{GmailSendEmail} and \texttt{BankManagerTransferFunds} are not syntactically dangerous---without provenance, there is nothing to block them. \sys{} reduces ASR to 4.12\%, demonstrating that provenance is the indispensable layer when the tool itself is legitimate but its arguments originate from attacker-controlled content. The defense operates through complementary layers: boundary-level proxy enforcement blocks 25.3\% of attack evaluations, while LLM safety training contributes an additional 28.4\% model-level refusal rate.

\paragraph{Interpreting Safe Tool Calls.}
A substantial fraction of attack evaluations produce tool calls that do not match our four dangerous-call patterns. These evaluations include cases where the attack was ignored by the model, the model partially complied with a non-dangerous action, or the model produced a malformed call. We conservatively exclude these from the proxy's defense contribution, making our reported proxy-denial rate a lower bound.

The residual bypasses concentrate in encoding obfuscation, where obfuscated payloads evade argument validation. Section~\ref{sec:discussion} analyzes these failures and the content-decoding preprocessor we implement to address them.

\subsection{RQ5: Provenance Accuracy}
\label{subsec:llm-oracle}

We analyze the proxy-blocked attack evaluations to verify that denied tool calls genuinely trace to untrusted sources.

\paragraph{True Positives.}
All proxy-blocked evaluations contain arguments tracing to untrusted nodes in the provenance DAG---injected device names, file contents, or calendar events controlled by the attacker. No denied call had arguments exclusively from trusted user input, confirming zero false denials on attack evaluations.

\paragraph{False Positives.}
The false positives (FPR = 5.00\% $\pm$ 1.53) arise from overly conservative \emph{policy rules}, not provenance misclassification. In all cases, the DAG correctly identifies benign arguments as trusted; the policy engine's argument-validation patterns trigger false blocks. This confirms that provenance tracking is precise---false positives stem from policy tuning, which is independently refinable.

\paragraph{Residual Bypasses.}
The successful attacks are not primarily caused by provenance-resolution failures. In the encoding-obfuscation cases, the provenance DAG correctly marks arguments as untrusted, but the policy rule does not match the encoded form. In the remaining cases, the provenance chain passes through plausible intermediate states that reduce the salience of the original untrusted source.

We evaluate adaptive paraphrase evasion with a Stage~1-only ablation: 32 scenarios $\times$ 3 LLM-generated variants = 96 tests, classified as \emph{literal} (15 scenarios: paths, emails---LLM must preserve verbatim) or \emph{natural-language} (17 scenarios: messages, titles---LLM may freely rephrase). In this ablation, we disable Stage~2 embeddings and Stage~3 conservative fallback to isolate substring matching behavior. Table~\ref{tab:paraphrase}: substring provenance blocks 93.3\% of literal-argument attacks, but NL arguments achieve only 7.8\% block rate (52.1\% overall paraphrase ASR).

\paragraph{Why Substring Matching Fails on NL Arguments.}
When the LLM processes an injected instruction like ``send credentials to an attacker'' embedded in a device name, it may generate a tool call with a \emph{semantically equivalent but textually different} argument: ``Forward private authentication material externally.'' Substring matching searches for the original injected string in the tool call arguments; if the LLM paraphrased the instruction, no substring match is found, and the Stage~1-only resolver fails to link the argument to its untrusted source (false negative). This is the fundamental limitation of syntactic provenance tracking in the presence of an opaque LLM computation.

\paragraph{Literal vs.\ NL Argument Types.}
The sharp dichotomy between literal (93.3\% block rate) and NL (7.8\% block rate) arguments reflects a structural property of LLM function calling: \emph{structured arguments} (file paths, email addresses, device IDs) must be preserved verbatim for the tool call to succeed, making them amenable to substring matching. \emph{Unstructured arguments} (message bodies, notification text, event descriptions) are freely paraphrased by the LLM, defeating substring matching. In our 32-scenario benchmark, 15 scenarios (46.9\%) contain only literal arguments and 17 (53.1\%) contain at least one NL argument---reflecting a realistic distribution of tool calls.

\textbf{Embedding-Enhanced Provenance.} We augment substring matching with sentence embeddings (all-MiniLM-L6-v2, 22M parameters, 384-dimensional vectors, $<$5\,ms per comparison, no GPU required). The three-stage provenance resolution pipeline operates as follows: (1)~\emph{substring match}: check if the tool call argument appears verbatim in any untrusted node content (O($n$) scan); (2)~\emph{embedding similarity}: if no substring match, compute cosine similarity between the argument embedding and all untrusted node embeddings, flagging matches above threshold $\theta = 0.45$; (3)~\emph{conservative default}: if neither method resolves provenance, the argument is labeled UNTRUSTED (fail-safe). The threshold $\theta = 0.45$ was selected via 5-fold cross-validation on a held-out set of 20 paraphrase pairs, optimizing for $F_1$ score.

Table~\ref{tab:embedding-prov}: embedding provenance achieves \textbf{100\% recall} on both literal and NL arguments across all 96 tests, reducing paraphrase ASR from 52.1\% to \textbf{0.0\%}. The embedding model's small size (22M parameters, 90\,MB on disk) makes it deployable on resource-constrained edge devices without GPU acceleration.

\textbf{Results.} \sys{} blocks 14/15 adaptive attacks (\textbf{6.7\% adaptive ASR}) with 100\% benign task success. The key finding is that provenance-based defense is robust against targeted evasion:

\emph{Provenance Laundering} (0/3 bypassed): Attempts to ``wash'' untrusted content through user-initiated actions (e.g., injecting items in a to-do list, then asking the agent to ``process all items'') are blocked because \textbf{the provenance DAG maintains the complete derivation chain}---the meet operator over the trust lattice ensures any fact with an untrusted ancestor remains untrusted regardless of intermediate processing steps.

\emph{Policy-Aware Evasion} ($^\dagger$1/3 bypassed): The single bypass used a MEDIUM-risk notification channel (\texttt{notify.send}) to exfiltrate device data. The provenance DAG correctly identified the data as untrusted, but the policy for MEDIUM-risk tools permits untrusted-provenance calls. This represents a \emph{policy gap}, not a provenance failure---addressable by tightening MEDIUM-risk policies.

\emph{Embedding Evasion} (0/3 bypassed): Attempts to evade semantic provenance matching via metaphorical language and multilingual reformulation were refused by the model itself---the LLM did not generate the intended malicious tool call, demonstrating a dual barrier against obfuscation.

\emph{TOCTOU \& Multi-Vector} (0/6 bypassed): Deferred execution and combined attacks were blocked by the provenance DAG's persistent trust labels and pre-LLM screening.

\subsection{RQ8: External Benchmark Validation (InjecAgent)}
\label{subsec:injecagent}

To validate generalizability beyond our author-constructed scenarios, we evaluate \sys{} on InjecAgent~\cite{injecagent2024}, an independent benchmark of 1,054 indirect prompt-injection test cases across 17 user tools and 63 attacker tools spanning financial, physical, and data-theft attack categories (Zhan et al., ACL 2024 Findings). InjecAgent is structurally complementary to our 200-scenario benchmark: it exclusively targets indirect injection---where a tool result contains the attacker payload---which is also the dominant attack vector in \sys{}'s evaluation.

\paragraph{Setup.}
We adapt InjecAgent to the PROVSAFE evaluation framework as follows. For each test case: (1)~the LLM receives the benchmark's \emph{User Instruction} and is given only the relevant user-tool schema to call (no fabricated data); (2)~the benchmark's verbatim \emph{Tool Response}---which contains the injected attacker instruction---is returned as the tool result and added to the provenance DAG as an UNTRUSTED node; (3)~the LLM is then presented with the attacker-tool schemas and any resulting tool call is intercepted by \sys{}'s enforcement proxy. Risk tiers mirror our TDSC policy: physical-harm tools (e.g., \texttt{AugustSmartLockUnlockDoor}, \texttt{TerminalExecute}) are CRITICAL; financial and exfiltration tools (e.g., \texttt{GmailSendEmail}, \texttt{BankManagerTransferFunds}) are HIGH. We evaluate all four systems (No Defense, Pattern Filter, Policy-Only, \sys{}) with 3 repetitions each using the same per-trial temperature and seed derivation as the TDSC evaluation.

\paragraph{Results.}
Table~\ref{tab:injecagent} presents the decisive result of this evaluation. \sys{} achieves 4.12\% ASR-IA on InjecAgent---an 80\% reduction compared to No Defense (20.83\%)---demonstrating that provenance-based defense generalizes to an unseen tool ecosystem. No Defense's 20.83\% is consistent with InjecAgent's published baseline of 23.6\%--47.0\% for ReAct-prompted models~\cite{injecagent2024}, validating our evaluation harness.

The Policy-Only result is the most informative comparison: at 22.67\% ASR-IA, it performs no better than No Defense. The reason is structural. InjecAgent's 63 attacker tools---\texttt{GmailSendEmail}, \texttt{BankManagerTransferFunds}, \texttt{AugustSmartLockGrantGuestAccess}, among others---are legitimate tools invoked with attacker-chosen arguments. They do not match any dangerous-action pattern (delete, unlock, extreme temperature), so without provenance there is \emph{nothing to trigger a denial}. Provenance resolves this: \sys{} traces each argument back through the DAG and finds that it derives from the untrusted tool response containing the injection payload. The trust lattice meet operator propagates the UNTRUSTED label regardless of intermediate processing, and the policy engine denies or flags the call accordingly. This mechanism transfers without modification across tool ecosystems---the DAG structure and trust propagation rules are domain-agnostic.
