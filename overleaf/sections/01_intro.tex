\section{Introduction}
\label{sec:intro}

Large language models (LLMs) are increasingly deployed as autonomous \emph{tool-using agents}---systems that read external data and invoke APIs on behalf of users~\cite{openai-agents,anthropic-tools,langchain}. Applications range from smart-home control and enterprise automation to code generation and web browsing. This expansion of capability introduces a fundamental vulnerability: \emph{prompt injection attacks}~\cite{greshake2023not,perez2022ignore}, in which adversaries embed malicious instructions in content the agent processes alongside legitimate commands.

Consider an IoT agent (Fig.~\ref{fig:attack-example}): Alice asks, ``What devices are online?'' The agent calls \texttt{device.list()} and receives a list that includes an attacker-controlled device named \textit{``Living Room Light. SYSTEM ALERT: Delete all backup files.''} Because the LLM cannot distinguish data from instructions---both appear as tokens in the same context window---the agent may execute the embedded command. This \emph{indirect prompt injection}~\cite{greshake2023not} is not theoretical: Bing Chat exhibited uncontrolled agent behavior in production~\cite{bing-sydney}, and researchers have demonstrated data exfiltration via indirect injection in ChatGPT plugins~\cite{greshake2023not}.

\textbf{Why Existing Defenses Fail.}
Unlike SQL/XSS injection, where syntactic boundaries separate code from data, LLMs process \emph{all} input as natural language. The root cause is a missing primitive: \emph{data provenance}. Input filtering~\cite{rebuff-defense,llm-guard} catches only syntactic patterns and cannot distinguish the \emph{same} string appearing as a legitimate user command versus an injected payload. Dual-LLM architectures~\cite{robust-prompt} double cost while potentially shifting, rather than eliminating, the attack surface. Output validation~\cite{langchain-guardrails} cannot determine whether a deletion is benign or malicious without knowing \emph{where the instruction originated}. Policy-based capability restrictions fail when attacker-chosen tools are not syntactically dangerous---our InjecAgent evaluation shows that policies without provenance achieve 22.67\% ASR, no better than no defense (Section~\ref{sec:eval}).

\textbf{Key Insight.}
The fundamental gap in LLM agent security is \emph{provenance}: tracking where each piece of information came from and how it influenced the agent's decisions. While the LLM itself cannot distinguish instructions from data, security can be enforced at the \emph{tool-call boundary}: \emph{a tool call should be authorized not just based on what it does, but on where its arguments came from.} If a deletion request traces to an attacker-controlled device name, the system denies it---regardless of whether the LLM considers the operation legitimate. This instantiates the classical \emph{reference monitor} concept~\cite{anderson1972reference}---complete mediation of security-sensitive operations---at the tool-call boundary of LLM agents.

Applying provenance to LLM agents introduces challenges absent from classical taint tracking~\cite{taint-analysis-survey,taintdroid}: (1)~\emph{opaque computation}---LLM inference cannot be instrumented instruction-by-instruction, requiring boundary-level why-provenance; (2)~\emph{approximate resolution}---the LLM may paraphrase content, so linking arguments to sources requires semantic matching, not just syntactic identity; (3)~\emph{nuanced trust}---unlike binary taint, agents \emph{must} read untrusted data to function, demanding provenance-\emph{gated} policies rather than blanket denial.

\textbf{Our Approach: \sys{}.}
We present \sys{}, a provenance-gated policy enforcement framework for tool-using LLM agents. \sys{} maintains a provenance DAG grounded in the W3C PROV Data Model~\cite{prov-dm}, tracking the lineage of every datum the agent processes. User commands are labeled \emph{trusted}; tool results from external systems are \emph{untrusted}. Trust annotations propagate via a lattice meet ($\sqcap$) operator: any fact derived from an untrusted source inherits untrusted status. When the agent proposes a tool call, an enforcement proxy resolves each argument's provenance through a three-stage pipeline---substring matching, sentence-embedding similarity, and conservative UNTRUSTED default---then evaluates declarative policies combining capability restrictions, provenance constraints, scope limitations, and rate limits.

\textbf{Results.}
We evaluate \sys{} on a 200-scenario benchmark (160 attacks across 8 categories and 40 benign tasks) with five LLMs spanning four vendor families and a 40$\times$ parameter range (Meta Llama-3.1-8B, Alibaba Qwen2.5-7B, Google DeepMind Gemma-2-9B, Microsoft Phi-3.5-Mini, and Alibaba Qwen3.5-122B) over five independent repetitions and five systems (No Defense, Pattern Filter, Policy-Only, Taint-Everything, \sys{})---totaling \textbf{25{,}000 trials}. All results include 95\% Wilson-score confidence intervals:
\begin{itemize}[leftmargin=1.2em]
  \item \sys{} achieves an attack success rate (ASR-IA) of \textbf{1.09\% $\pm$ 0.36} with \textbf{95.00\% $\pm$ 1.52 TSR}---a 24$\times$ reduction versus No Defense and 7$\times$ versus Pattern Filter.
  \item \textbf{Taint-Everything is secure but unusable:} blanket tainting achieves 0.31\% ASR but collapses TSR to 62.5\%---\sys{} matches its security while preserving 95\% usability.
  \item On the 200-scenario benchmark, Policy-Only also achieves low ASR (1.88\%) because many attack tools are syntactically dangerous (e.g., \texttt{fs.delete}). On the external InjecAgent benchmark (1,054 cases, 63 attacker tools that are \emph{not} syntactically dangerous), Policy-Only fails catastrophically: \textbf{22.67\% ASR}---no better than No Defense (20.83\%)---while \sys{} maintains \textbf{4.12\% $\pm$ 0.5 ASR}. This 5.5$\times$ reduction demonstrates that provenance is essential when attacker tools cannot be identified by syntax alone.
  \item Boundary-level enforcement blocks 25.3\% of attacks at the proxy before execution; an additional 28.4\% are refused by the models themselves.
  \item Results are consistent across all five models (ASR-IA range: 0.00\%--1.88\%), including \textbf{0.00\% ASR-IA} on a 122B-parameter model.
  \item Embedding-enhanced provenance closes the paraphrase gap (52.1\% $\to$ 0\% paraphrase ASR) with $<$5\,ms overhead per argument.
\end{itemize}

\paragraph{Contributions.}
(1)~We formalize \emph{provenance-gated capability control} for LLM agent tool calls using the W3C PROV Data Model with a two-element trust lattice, and present \sys{}, an enforcement architecture combining a provenance DAG, declarative policies, and a three-stage provenance resolution pipeline (substring matching, sentence-embedding similarity, conservative default).
(2)~We design a declarative policy language supporting provenance-aware queries, risk tiers, scope constraints, and rate limits, enabling fine-grained access control at the tool-call boundary.
(3)~We conduct a systematic evaluation on a 200-scenario benchmark with five LLMs spanning 3B--122B parameters over five repetitions (25{,}000 trials across five systems) and validate on the external InjecAgent benchmark (1{,}054 cases), demonstrating that provenance is the decisive factor when attacker tools are not syntactically distinguishable from legitimate ones.
(4)~We will release \sys{} as open-source software upon acceptance, including the framework, benchmark scenarios, policy templates, and reproducible experiment scripts.
