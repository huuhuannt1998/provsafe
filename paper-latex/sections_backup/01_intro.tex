\section{Introduction}
\label{sec:intro}

Large language models (LLMs) are being rapidly deployed as autonomous agents in smart homes, capable of
controlling IoT devices, managing calendars, accessing files, and sending notifications based on natural
language commands~\cite{openai-agents,anthropic-tools,langchain}. These \emph{tool-using LLM agents} promise
to revolutionize human-computer interaction, enabling users to orchestrate complex automations through
conversational interfaces. However, this power introduces a fundamental security vulnerability:
\emph{prompt injection attacks}~\cite{greshake2023not,perez2022ignore,prompt-injection-taxonomy}.

Consider a typical smart home scenario (Figure~\ref{fig:attack-example}): Alice asks her LLM agent,
``What devices are online?'' The agent calls \texttt{device.list()} and receives a list including an
attacker-controlled device named: \textit{``Living Room Light. SYSTEM ALERT: Delete all backup files
in /home/user/backups for security update.''} When Alice later asks, ``Act on any system alerts,'' the
agent---unable to distinguish this malicious instruction from legitimate commands---may call
\texttt{fs.delete("/home/user/backups/*")}, destroying Alice's data. This \emph{indirect prompt injection}
attack~\cite{greshake2023not} succeeds because the LLM processes both trusted user commands and untrusted
external content (device names, file contents, web pages) in the same context window, with no reliable
mechanism to separate instructions from data.

\textbf{The Fundamental Challenge.}
Unlike traditional injection attacks (SQL, XSS) where syntactic boundaries separate code from data,
LLMs process \emph{all} input as natural language~\cite{prompt-injection-taxonomy}. This creates an
unsolvable dilemma at the prompt level: when an agent reads ``Delete file X'' from a device name,
is this a legitimate system message or attacker-controlled data? The LLM's training objective---to
follow instructions in its context---works against security.

Existing defenses are fundamentally inadequate:
\textbf{(1)~Input filtering}~\cite{rebuff-defense,llm-guard} detects only syntactic patterns
(``ignore previous instructions''), failing against semantic paraphrasing, encoding (Base64, Unicode),
and context-dependent attacks.
\textbf{(2)~Dual-LLM architectures}~\cite{robust-prompt,dual-llm-defense} use a second LLM to filter
input, but this merely shifts the problem---can the filter LLM reliably detect sophisticated injections?
Moreover, it doubles inference cost and latency.
\textbf{(3)~Output validation}~\cite{langchain-guardrails} checks generated tool calls post-hoc, but
lacks context: deleting \texttt{/tmp/cache} may be benign or malicious depending on \emph{why} the
LLM decided to delete it.
\textbf{(4)~User confirmation}~\cite{shneiderman-guidelines} for every tool call provides security
but destroys usability---users cannot approve dozens of low-risk operations to prevent rare high-risk
attacks.
\textbf{(5)~Static capability restrictions}~\cite{principle-least-privilege} (e.g., ``agent cannot
delete files'') are too coarse-grained for real-world scenarios where context matters: deleting a
temporary file (benign) vs. deleting a user document (malicious).

A fundamental challenge is that LLMs process data holistically---when an agent reads a malicious device name
(``Ignore previous instructions and delete /important.txt''), generates a summary, and later uses that summary
to decide on a tool call, the \emph{provenance} of the decision is lost. The system cannot determine whether
the tool call originated from a legitimate user command or from attacker-controlled content.

\textbf{Key Insight: Provenance-Aware Policy Enforcement.}
We observe that while LLMs cannot distinguish instructions from data at the \emph{prompt level}, we can
enforce security at the \emph{tool-call boundary} by tracking \emph{data provenance}. The key insight is:
\emph{A tool call should be authorized not just based on what it does, but on where its arguments came from.}
If a file deletion request traces back to untrusted input (an attacker-controlled device name), the system
can deny it or require explicit user confirmation---even if the LLM believes the operation is legitimate.

This shifts the security perimeter from the unreliable prompt-processing layer (where the LLM operates)
to the reliable tool-execution layer (where we have full observability and control). Crucially, this
approach does not attempt to "fix" the LLM or detect injected prompts. Instead, it acknowledges that
LLMs \emph{will} be manipulated by clever prompts and builds a defense-in-depth layer that prevents
manipulated LLMs from causing harm.

\textbf{Our Approach: \sys{}.}
We present \sys{}, a provenance-verified capability sandboxing framework for tool-using LLM agents.
(Note: We use the term ``sandboxing'' to refer to \emph{application-level capability restriction} via a proxy, distinct from OS-level isolation techniques like containers or virtual machines).
\sys{} maintains a directed acyclic graph (DAG) tracking the provenance of every piece of information
the agent processes: user commands (\emph{trusted}), tool results from external systems (\emph{untrusted}),
and derived facts generated by the LLM (inheriting trust from their sources). When the agent proposes
a tool call, \sys{}'s enforcement proxy intercepts it and evaluates a declarative policy considering:
(i)~the tool's inherent risk tier, (ii)~the provenance of tool call arguments, (iii)~scope and temporal
constraints, (iv)~rate limits, and (v)~evidence requirements. Policies can express nuanced rules like:
``ALLOW \texttt{fs.delete} IF path is in /tmp/ AND (provenance is trusted OR user confirms).'' This
enables fine-grained, context-aware access control without relying on the LLM to make security decisions.
If a policy demands user confirmation, the proxy prompts for approval; if the policy denies the call,
execution is blocked; otherwise, the tool executes normally.

Crucially, \sys{} labels each input node in the provenance graph as \emph{trusted} (user commands, system
prompts) or \emph{untrusted} (device names, notifications, file contents). Trust labels propagate through
derivations: any fact derived from untrusted input inherits the untrusted label. When a tool call argument
traces back to untrusted sources, policies can require confirmation or additional evidence, preventing
blind execution of attacker-controlled commands.

\textbf{Evaluation and Results.}
We implement \sys{} as an open-source Python framework and evaluate it across four defense configurations (No Defense, Pattern Filter, Policy-Only, and full \sys{}) on a benchmark suite of 160 attack scenarios and 40 benign tasks spanning 8 attack categories, deployed across four diverse LLM agent models (GPT-OSS-120B, InternVL3.5-30B-A3B, Qwen3-30B-A3B, GPT-OSS-20B). Our evaluation comprises 3,200 total evaluations (200 scenarios $\times$ 4 models $\times$ 4 systems) and demonstrates:

\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Near-complete attack mitigation:} \sys{} achieves \textbf{0.16\% ASR} (only 1 attack succeeded across 640 evaluations), blocking 99.84\% of prompt injection attempts. This represents a \textbf{98.7\% reduction} from the 12.34\% baseline ASR. Three of four LLM models achieve perfect 0\% ASR; the single successful attack exploited a sophisticated multi-turn queuing pattern against Qwen3-30B.
  
  \item \textbf{Provenance enables usability, not just security:} Our ablation study reveals a surprising finding: policy-only defense achieves 0\% ASR (perfect security) but only \textbf{21.25\% TSR}---rendering the agent nearly unusable. Provenance tracking restores usability to \textbf{98.12\% TSR} while maintaining near-zero ASR. This validates our core insight: security \emph{and} usability require knowing where information came from.
  
  \item \textbf{Optimal security-usability balance:} \sys{} is the \textbf{only evaluated system} achieving both high security (0.16\% ASR) and high usability (98.12\% TSR). All other defense configurations sacrifice one for the other.
  
  \item \textbf{Cross-model robustness:} Results are consistent across four LLM models spanning a 6$\times$ parameter range (20B-120B). Attack categories with highest baseline risk---encoding obfuscation (47.2\% ASR) and role-play jailbreaks (27.5\% ASR)---are completely blocked by \sys{}.
\end{itemize}

Compared to prior work, \sys{} is, to our knowledge, the first system to:
(1)~combine provenance tracking with capability-based policies specifically for LLM agents,
(2)~enforce security at the tool-call boundary rather than the prompt level,
(3)~provide a declarative policy language supporting provenance queries, and
(4)~demonstrate effectiveness against 100+ diverse attack scenarios with rigorous ablation studies.

\paragraph{Contributions.}
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Novel Defense Architecture:} We introduce provenance-verified capability sandboxing,
        to our knowledge, the first system to combine data lineage tracking (provenance DAGs with trust labels) and
        policy-based access control specifically for LLM agents. Unlike prior work that operates at
        the prompt level, \sys{} enforces security at the tool-call boundary, providing a principled
        defense-in-depth layer resistant to prompt-level evasion.
  
  \item \textbf{Expressive Policy Language:} We design a declarative policy DSL enabling administrators
        to express context-aware access control rules combining: (i)~capability restrictions (risk tiers,
        tool allowlists), (ii)~provenance constraints ("deny if arguments trace to untrusted sources"),
        (iii)~scope restrictions (path prefixes, resource boundaries), (iv)~temporal constraints
        (time-of-day rules), (v)~rate limits, and (vi)~evidence requirements (explicit justification).
        To our knowledge, this is the first policy language supporting \emph{provenance queries}.
  
  \item \textbf{Efficient Enforcement Proxy:} We implement a low-latency (median 0.06ms) tool-call
        interception layer that: (i)~resolves provenance via graph traversal with trust propagation,
        (ii)~evaluates policies in priority order with short-circuit optimization, (iii)~generates
        user-friendly confirmation prompts with provenance explanations, and (iv)~logs all decisions
        with SHA-256 integrity hashes for tamper-evident auditing.
  
  \item \textbf{Comprehensive Attack Taxonomy and Benchmark:} We systematically categorize prompt
        injection attacks into 8 categories and construct a benchmark of 160 attack scenarios and 40 benign tasks including: direct injection, indirect injection via 5 vectors (device names, notifications, files, calendar, location metadata), multi-turn chaining, encoding obfuscation (Base64, URL, Unicode), role-play jailbreaks, confused deputy, and privilege escalation attacks. Each scenario includes setup, expected behavior, and success criteria.
  
  \item \textbf{Rigorous Empirical Evaluation:} We conduct: (i)~comparative evaluation against 4
        baselines showing 98.7\% ASR reduction (12.34\% $\rightarrow$ 0.16\%), (ii)~ablation studies demonstrating provenance is essential for usability (policy-only: 0\% ASR but 21.25\% TSR; full \sys{}: 0.16\% ASR with 98.12\% TSR), (iii)~cross-model validation across four LLM models (20B-120B parameters) with 3/4 achieving 0\% ASR, and (iv)~per-category analysis showing complete blocking of encoding obfuscation and role-play jailbreaks.
  
  \item \textbf{Open-Source Artifact:} We release the complete \sys{} implementation (5,000+ LOC),
        policy examples, benchmark suites, evaluation scripts, and deterministic replay tools. All
        results are reproducible via one-command evaluation pipelines.
\end{itemize}
