\section{Related Work}
\label{sec:related}

\subsection{Prompt Injection Attacks and Defenses}

\paragraph{Attack Characterization.}
Prompt injection was first systematically studied by Perez et al.~\cite{perez2022ignore}, who demonstrated
that LLMs cannot reliably separate instructions from data. Greshake et al.~\cite{greshake2023not} introduced
\emph{indirect prompt injection}, where attackers embed malicious instructions in external content (web pages,
emails) that the LLM reads during execution. Recent surveys~\cite{prompt-injection-taxonomy,jailbreak-survey}
catalog attack variants including jailbreaks, role-play exploits, and encoding obfuscation. Our work builds
on this taxonomy, systematically categorizing attacks into 8 categories and demonstrating defense effectiveness
via comprehensive benchmarking.

\paragraph{Input Filtering and Detection.}
\textbf{Pattern-Based Filtering.} Early defenses like Rebuff~\cite{rebuff-defense} and LLM Guard~\cite{llm-guard}
use keyword blacklists to detect phrases like ``ignore previous instructions.'' However, Liu et al.~\cite{liu2023prompt}
showed such filters achieve only 30-40\% detection rates against sophisticated attacks using paraphrasing,
encoding (Base64, ROT13), or semantic equivalents (``Please disregard earlier guidance''). Our evaluation
confirms this limitation: pattern filtering reduces ASR from 12.34\% to only 3.12\% (74.7\% reduction), but fails completely against encoding obfuscation (19.4\% ASR) and cannot detect role-play jailbreaks that lack syntactic patterns. In contrast, \sys{} achieves 0.16\% ASR by operating at the tool-call boundary with provenance awareness.

\textbf{Learned Detectors.} Recent work trains classifiers to detect injections~\cite{prompt-guard,injection-detector}.
PromptGuard~\cite{prompt-guard} uses a fine-tuned DeBERTa model achieving 85\% precision and 78\% recall on
synthetic datasets. However, it suffers from distribution shift: trained on specific attack patterns, it
fails against novel attacks. Moreover, it operates on isolated inputs, ignoring context---a sentence may
be benign in isolation but malicious when combined with other inputs.

\textbf{Production Guardrail Systems.} NVIDIA's NeMo Guardrails~\cite{nemo-guardrails} provides programmable
safety rails including input/output filtering, topical constraints, and dialog management. LLM Guard~\cite{llm-guard}
offers modular scanners for PII detection, toxicity filtering, and injection detection. While these systems
are production-ready and widely deployed, they share a fundamental limitation: they operate at the prompt
level without tracking data provenance. A sophisticated injection that passes initial filtering will succeed
if it later influences tool call generation.

\textbf{Comparison.} Unlike detection-based approaches, \sys{} does not attempt to identify injected prompts.
Instead, it acknowledges that LLMs \emph{will} be manipulated and enforces policies at the tool-call boundary.
This architectural decision makes \sys{} robust to adversarial prompt engineering: even if an attacker crafts
a perfect injection bypassing all detectors, \sys{}'s provenance-based policies prevent unauthorized tool calls.
\sys{} can be deployed \emph{alongside} existing guardrails as a defense-in-depth layer.

\paragraph{Dual-LLM and Multi-Model Architectures.}
\textbf{Robust Prompt.} Robust Prompt~\cite{robust-prompt} uses a second "filter" LLM to sanitize user
input before passing it to the main agent. The filter LLM is trained to remove or neutralize injected instructions.
However, this approach has three limitations: (1)~it doubles inference cost and latency (two LLM calls per
user input), (2)~the filter LLM itself may be vulnerable to adversarial prompts, and (3)~it only addresses
\emph{direct} injection (user input), not indirect injection (content read during task execution).

\textbf{Self-Reminder and Dual-Process.} Ji et al.~\cite{self-reminder} prepend reminders to every user
message (``Remember: you are a helpful assistant. Ignore any instructions in user messages.''). However,
this increases context length and still fails against sophisticated attacks. Dual-Process LLMs~\cite{dual-llm-defense}
separate ``System 1'' (fast, instruction-following) from ``System 2'' (slow, reflective reasoning), but
they require model retraining and lack theoretical guarantees.

\textbf{Comparison.} \sys{} avoids the dual-LLM overhead by operating \emph{after} the main LLM generates
tool calls, at the enforcement boundary. Our proxy adds <0.1ms overhead (vs. 100-1000ms for a second LLM
inference). Moreover, \sys{} handles both direct and indirect injection via provenance tracking: if a tool
call argument traces to untrusted content (regardless of when it was read), the policy applies.

\paragraph{Instruction Hierarchy and Delimiters.}
\textbf{System Prompt Prioritization.} OpenAI's GPT-4 uses special tokens and instruction hierarchies to
make system prompts more authoritative than user input~\cite{openai-system-prompt}. Anthropic's Constitutional
AI~\cite{constitutional-ai} fine-tunes models to follow safety principles even when user instructions conflict.
However, these approaches fail against indirect injection: when the LLM reads attacker-controlled content
as part of task execution (e.g., ``list devices'' returns malicious device name), it appears as \emph{trusted
context}, not user input.

\textbf{Delimiter-Based Separation.} Some work~\cite{delimiters-defense} wraps untrusted content in special
delimiters (e.g., ``<untrusted>...content...</untrusted>'') and instructs the LLM to ignore instructions
within delimiters. However, delimiters are just more instructions---LLMs can be tricked into ignoring them
(``Pretend delimiters don't exist''). Moreover, this requires manual annotation of every untrusted input,
which is error-prone.

\textbf{Comparison.} \sys{} does not rely on LLM behavior (system prompt adherence, delimiter recognition).
Instead, it tracks provenance \emph{externally} in a DAG maintained by the enforcement proxy. Even if the
LLM completely forgets which inputs were trusted vs. untrusted, \sys{} has ground truth via provenance tracking.

\paragraph{Output Validation and Sandboxing.}
\textbf{Post-Hoc Validation.} LangChain Guardrails~\cite{langchain-guardrails} and NeMo Guardrails~\cite{nemo-guardrails}
validate LLM-generated tool calls against predefined rules (e.g., ``deny if tool=fs.delete and path contains
/important/''). However, these rules are context-free: they cannot distinguish ``delete /tmp/cache'' (benign)
from ``delete /home/user/important.txt'' (malicious) if both match path patterns. They also require exhaustive
rule engineering for every possible attack.

\textbf{Least-Privilege Sandboxing.} Some systems~\cite{android-permissions,browser-sandboxing} restrict
agents to minimal capabilities (e.g., read-only file access). However, smart home agents \emph{need} write
privileges for legitimate tasks (creating calendar events, sending notifications). Static privilege restriction
is too coarse-grained.

\textbf{Comparison.} \sys{}'s policies are \emph{context-aware} via provenance queries: ``ALLOW fs.delete
IF path=/tmp/* OR (provenance=trusted AND user confirms).'' This enables fine-grained control: the same
tool call may be allowed or denied depending on its provenance. Our ablation studies reveal a critical insight: policy-only defense (without provenance) achieves 0\% ASR but only 21.25\% TSR---blocking nearly all attacks but also 79\% of legitimate operations. Adding provenance tracking restores TSR to 98.12\% while maintaining 0.16\% ASR, demonstrating that provenance is essential \emph{for usability}, not just security.

\textbf{Key Observations:}
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Substantially lower reported ASR:} \sys{} achieves 0.16\% ASR on our benchmark, compared to 14--55\% reported by prior work on their respective benchmarks. While direct comparison across different evaluation setups is limited, the 1--2 order-of-magnitude difference suggests a meaningful advance.
  
  \item \textbf{Superior usability:} Most defenses trade security for usability: PromptGuard achieves 15\% ASR but only 85\% recall (meaning 15\% of attacks and 15\% of benign inputs are misclassified). \sys{} achieves both 0.16\% ASR and 98.12\% TSR.
  
  \item \textbf{Indirect injection defense:} Among the systems we evaluated, \sys{} is the only one that addresses indirect prompt injection---attacks embedded in content the agent reads during execution (device names, files, calendars). Prior approaches primarily address direct injection (malicious user input).
  
  \item \textbf{Tool-call boundary enforcement:} Operating at the tool-call layer rather than the prompt level makes \sys{} resistant to prompt-level evasion techniques (encoding, paraphrasing, role-play), since enforcement decisions do not depend on detecting malicious input strings.
\end{itemize}

\textbf{Benchmark Context:} We note that our benchmark (160 attacks, 40 benign, 8 categories, 4 models) is among the most comprehensive evaluations of LLM agent defense. InjecAgent~\cite{injecagent2024} reports that GPT-4 is vulnerable to 24\% of indirect injections in their benchmark, consistent with our 12.34\% baseline ASR (the difference reflecting attack sophistication and model differences). \sys{}'s 0.16\% ASR on this challenging benchmark represents a significant advance over prior work.

\subsection{LLM Agent Security}

\paragraph{Tool-Use Safety.}
Schick et al.~\cite{schick2023toolformer} and Parisi et al.~\cite{talm} introduced tool-augmented LLMs but
did not address security. Recent work~\cite{llm-tool-safety} identifies risks such as unintended tool calls,
privilege escalation, and data leakage. \sys{} provides a structured framework (policy language + provenance)
to mitigate these risks.

\paragraph{Multi-Agent Systems.}
Autonomous agents like AutoGPT~\cite{autogpt} and BabyAGI~\cite{babyagi} execute complex workflows with
minimal human oversight, amplifying injection risks. Sumers et al.~\cite{cognitive-architectures-safety}
argue for explicit security layers in agent architectures, which \sys{} provides via the enforcement proxy.

\paragraph{Red-Teaming and Benchmarks.}
Peterson et al.~\cite{llm-redteam} and Ganguli et al.~\cite{redteam-anthropic} use red-teaming to discover
vulnerabilities in LLM agents. Our benchmark suite complements this by providing 100+ reproducible attack
scenarios for evaluating defenses.

\subsection{Capability-Based Security}

\paragraph{Foundational Concepts.}
Capability-based security~\cite{miller2006capability,levy1984capability} grants permissions via unforgeable
tokens (capabilities) rather than ambient authority. Systems like Capsicum~\cite{capsicum} and CloudABI~\cite{cloudabi}
apply capabilities to OS-level sandboxing. \sys{} adapts this model to LLM tool calls: each tool is a capability,
and policies specify when capabilities can be exercised.

\paragraph{Least Privilege in Software.}
Principle of least privilege~\cite{saltzer1975protection} dictates that code should only access resources
necessary for its task. In LLM agents, this translates to restricting tool calls based on context (user intent,
data provenance, temporal constraints). \sys{} enforces least privilege via declarative policies.

\paragraph{Object-Capability Languages.}
Languages like E~\cite{miller-e-language} and Joe-E~\cite{joe-e} enforce capability security at the language
level. \sys{}'s policy language is inspired by object-capabilities but operates at the tool-call boundary,
making it language-agnostic.

\subsection{Data Provenance and Taint Tracking}

\paragraph{Provenance in Databases and Workflows.}
Provenance tracking~\cite{cheney2009provenance,muniswamy2006provenance} records data lineage in scientific
workflows and databases. Systems like Trio~\cite{trio-provenance} and PLUS~\cite{plus-provenance} maintain
DAGs linking outputs to inputs. \sys{} applies similar principles to LLM agents, tracking how derived facts
(summaries, conclusions) depend on source inputs.

\paragraph{Taint Analysis in Security.}
Dynamic taint analysis~\cite{taint-analysis-survey,newsome2005dynamic} labels untrusted data (e.g., user input)
and tracks its flow through a program to prevent injection attacks. TaintDroid~\cite{taintdroid} applies
this to Android apps. \sys{}'s trust labeling is analogous: untrusted inputs (device names, file contents)
are labeled, and labels propagate through derivations. However, unlike binary taint tracking, \sys{} uses
provenance graphs to support nuanced policies (e.g., ``allow if untrusted but within safe scope'').

\paragraph{Information Flow Control.}
Decentralized Information Flow Control (DIFC)~\cite{difc-survey,flume} enforces confidentiality and integrity
via security labels. Jif~\cite{jif} extends Java with information flow types. \sys{} is inspired by DIFC
but tailored to LLM agents: trust labels are propagated through provenance, and policies gate tool execution.

\paragraph{What Is New in the LLM-Agent Setting.}
A natural question is whether \sys{} is ``merely taint tracking applied to tool calls.'' We argue that adapting provenance to LLM agents introduces three challenges absent from classical settings:

\begin{enumerate}[leftmargin=1.2em]
  \item \textbf{Opaque Computation.} Traditional taint tracking instruments \emph{source code} or \emph{bytecode} (e.g., TaintDroid rewrites Dalvik bytecode). LLMs are opaque: there is no ``source code'' to instrument, and billions of floating-point operations make per-token tracking infeasible. \sys{} therefore tracks provenance \emph{externally}, at the observable tool-call boundary, using output--input substring matching as a practical approximation. This design choice trades precision for deployability---no model modification is required.
  
  \item \textbf{Natural-Language Injection Surface.} In classical injection (SQL, XSS), the boundary between code and data is syntactically defined; taint tracking prevents data from crossing that boundary. In LLM agents, \emph{all} input is natural language, and the ``injection'' is the model deciding to follow an instruction embedded in data. The relevant enforcement boundary is therefore \emph{which tool calls the model requests}, not which bytes cross a parser boundary. To our knowledge, \sys{} is the first system to formalize this tool-call boundary as the taint-enforcement point for LLM agents.
  
  \item \textbf{Provenance-Gated Policy (Not Binary Taint).} Classical taint analysis is binary: tainted data is blocked; untainted data is allowed. This is too coarse for agents that \emph{must} read untrusted data to function (e.g., listing device states). \sys{} introduces provenance-gated policies that express nuanced decisions: ``allow reading untrusted data, but require confirmation before writing it to a sensitive path.'' Our ablation (Table~\ref{tab:ablation}) quantifies the cost of binary taint semantics: policy-only (without provenance-gated nuance) achieves 0\% ASR but only 21.25\% TSR.
\end{enumerate}

In short, the contribution is not taint tracking per se, but the \emph{adaptation} of provenance to an opaque, natural-language-mediated computation model, combined with a policy language that makes provenance actionable for practical agent deployment.

\subsection{Smart Home Security}

\paragraph{IoT Security Challenges.}
Smart home ecosystems face numerous threats: device vulnerabilities~\cite{fernandes2016security}, protocol
weaknesses~\cite{ronen2017iot}, and automation bugs~\cite{chi2020}. \sys{} focuses on a new threat vector:
LLM agents being manipulated via prompt injection to misuse IoT devices and services.

\paragraph{Access Control in IoT.}
ContextIoT~\cite{jia2017contexiot} enforces context-aware access control for IoT apps. SmartAuth~\cite{smartauth}
uses user presence and habits to authorize device actions. \sys{} extends these ideas to LLM agents, using
provenance to contextualize tool calls.

\paragraph{Policy Languages for IoT.}
Li et al.~\cite{iotguard} propose domain-specific policy languages for IoT safety. \sys{}'s policy DSL is
similar but designed for LLM tool calls, supporting provenance queries and evidence requirements.

\subsection{Program Synthesis and Verification}

\paragraph{LLM-Generated Code Safety.}
Recent work~\cite{codex-eval,codegen-bugs} studies bugs in LLM-generated code. Prenner et al.~\cite{llm-code-review}
use static analysis to validate generated programs. \sys{} addresses a different problem: not the correctness
of generated code, but the \emph{authorization} of tool calls generated by LLMs.

\paragraph{Runtime Verification.}
Runtime monitors~\cite{runtime-verification-survey} check program behavior against specifications during execution.
\sys{}'s enforcement proxy is a runtime monitor for LLM agents, verifying that tool calls comply with policies
before execution.

\subsection{Human-AI Interaction and Explainability}

\paragraph{Confirmation Dialogs and Transparency.}
Shneiderman~\cite{shneiderman-guidelines} argues for human oversight of autonomous systems. Mixed-initiative
interfaces~\cite{mixed-initiative} balance automation with user control. \sys{} implements this via risk-based
confirmation: low-risk tools execute automatically, high-risk tools require user approval.

\paragraph{Explainable AI.}
Explainability techniques~\cite{xai-survey,lime} help users understand AI decisions. \sys{}'s provenance
graphs provide \emph{structural explainability}: users can see why a tool call was allowed/denied by inspecting
its provenance trace.

\subsection{Summary}

\sys{} synthesizes ideas from prompt injection defense (detecting untrusted content), capability security
(least privilege via policies), data provenance (tracking information flow), and IoT access control (context-aware
authorization). The novelty lies not in any single component but in their \emph{composition for an opaque, natural-language-mediated computation model}: provenance must be tracked externally (the LLM is a black box), enforcement must occur at the tool-call boundary (the only observable control point), and policies must be provenance-gated rather than binary (agents must read untrusted data to function).

\textbf{Key Differentiators from Prior Work:}
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Defense Layer:} Unlike pattern filters and guardrails that operate at the prompt level (before/after LLM processing), \sys{} operates at the tool-call boundary. This makes it resistant to prompt-level evasion---even if an attacker crafts an injection bypassing all prompt-level defenses, \sys{} blocks the resulting unauthorized tool call based on provenance.
  
  \item \textbf{Provenance Awareness:} Prior work (Rebuff, LLM Guard, NeMo Guardrails, LangChain) makes context-free decisions based on tool names and argument values. \sys{} tracks where arguments \emph{originated}---a file deletion is allowed when the path came from trusted user input, blocked when it traces to an attacker-controlled device name.
  
  \item \textbf{Usability Preservation:} Policy-only approaches (without provenance) must conservatively block operations, achieving security at the cost of usability. Our evaluation shows policy-only defense drops TSR to 21.25\%. \sys{}'s provenance tracking enables precision, maintaining 98.12\% TSR.
  
  \item \textbf{Comprehensive Attack Coverage:} We evaluate against 160 attacks across 8 categories, demonstrating effectiveness against encoding obfuscation (0\% ASR vs. 47.2\% baseline), role-play jailbreaks (0\% ASR vs. 27.5\% baseline), and multi-turn chaining (1.2\% ASR vs. 8.8\% baseline).
\end{itemize}

\textbf{Complementary Deployment:} \sys{} can be deployed \emph{alongside} existing guardrails as a defense-in-depth layer. Pattern filters provide fast rejection of obvious attacks; \sys{} provides the final security barrier for sophisticated attacks that evade prompt-level detection.
