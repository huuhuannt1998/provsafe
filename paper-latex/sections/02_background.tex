\section{Background}
\label{sec:background}

\subsection{Tool-Using LLM Agents}

Modern LLMs (GPT-4~\cite{openai-gpt4}, Claude~\cite{anthropic-claude}, LLaMA~\cite{llama}) support \emph{function calling}~\cite{schick2023toolformer}, enabling agents to interact with external systems. An LLM agent consists of a system prompt defining its role, a tool registry of callable functions with typed schemas, and an execution loop (receive input, generate tool calls, execute, iterate). In smart homes, this enables multi-step automation: listing calendar events, summarizing them, and sending a notification---all from a single user command. However, if an attacker controls content the agent reads (e.g., a calendar event title), injected instructions can hijack subsequent tool calls.

\subsection{Prompt Injection}

Prompt injection~\cite{perez2022ignore,greshake2023not} exploits the fact that LLMs process instructions and data in the same text stream, with no syntactic boundary (unlike SQL). \emph{Direct injection} embeds commands in user input; \emph{indirect injection} embeds them in content read during execution~\cite{greshake2023not} (device names, files, web pages). \emph{Chained attacks} combine vectors across turns. Existing defenses (input filtering, output validation, instruction hierarchy, blanket user confirmation) each fail on at least one axis: keyword filters are bypassed via paraphrasing/encoding; output validation lacks provenance context; instruction hierarchies do not cover indirect injection; confirmation for every call destroys usability.

\subsection{Capability Security and Provenance}

Capability-based access control~\cite{miller2006capability} grants permissions via unforgeable tokens rather than ambient authority. Data provenance~\cite{cheney2009provenance} tracks lineage---where data came from and how it was transformed. \sys{} synthesizes both: capabilities restrict tool use via policies, and provenance determines whether tool-call arguments trace to trusted or untrusted sources.
