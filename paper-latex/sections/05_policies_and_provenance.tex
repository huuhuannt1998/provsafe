\section{Policy Language and Provenance Tracking}
\label{sec:policies}

This section details \sys{}'s policy language and provenance tracking mechanism.

\subsection{Policy Language}

\sys{} policies are expressed in YAML for human readability and ease of configuration. This section details the language constructs.

\paragraph{Risk Tiers.}
Tools are categorized by inherent risk and sensitive scope. LOW-risk operations are read-only (e.g., \texttt{fs.read}, \texttt{calendar.list}), which cannot modify state or leak sensitive data beyond what the user already sees. MEDIUM-risk operations can create or modify data (e.g., \texttt{fs.write}, \texttt{calendar.create}), potentially introducing new unwanted state but often necessary for legitimate user tasks. HIGH-risk operations are destructive (e.g., \texttt{fs.delete}, \texttt{email.send}), which can permanently remove or exfiltrate data; these require extra scrutiny. CRITICAL-risk operations are system-level (e.g., \texttt{device.reboot}, \texttt{user.grant\_access}), affecting the entire system or user accounts; these are almost always confirmation-required or policy-denied unless explicitly user-authorized.

\paragraph{Policy Rules and Conditions.}
Each rule in a policy file specifies a name, a list of tools it applies to, a set of conditions, and an action. Rules are evaluated in priority order, and the first rule whose conditions match determines the outcome. Conditions can include tool filters (match specific tools by name or category), provenance trust (require arguments to be from trusted sources, untrusted sources, or allow either), scope constraints (restrict paths to specific prefixes, allowlists, or denylists), temporal constraints (restrict execution to certain times of day, days of week, etc.), rate limits (enforce maximum call frequency), and evidence requirements (demand the agent provide structured justification). Conditions can be combined with boolean AND/OR logic for expressive rules. For example:

\begin{verbatim}
rules:
  - name: "Allow benign file reads from home"
    tools: ["fs.read"]
    conditions:
      path_prefix: "/home/user/"
      provenance_trust: "trusted"
    action: ALLOW
  
  - name: "Require confirmation for untrusted deletes"
    tools: ["fs.delete"]
    conditions:
      risk_tier: HIGH
      provenance_trust: "untrusted"
      path_contains: "/home/"
    action: REQUIRE_CONFIRMATION
    
  - name: "Deny all system file access"
    tools: ["fs.read", "fs.write"]
    conditions:
      path_prefix: ["/etc/", "/sys/", "/proc/"]
    action: DENY
\end{verbatim}

\paragraph{Actions.}
Each rule specifies an action to take when its conditions match. The ALLOW action executes the tool call immediately without further checks. The DENY action blocks the tool call and returns an error to the agent. The REQUIRE\_CONFIRMATION action prompts the user with details of the proposed tool call and provenance information, waiting for user approval before executing or denying. This three-action model balances security (DENY when unsafe, REQUIRE\_CONFIRMATION for high-risk, ALLOW for benign) with usability (not every call is blocked, but risky calls get human review).

\paragraph{Evaluation Semantics.}
Rules are evaluated in priority order from top to bottom of the policy file. The first matching rule determines the action; subsequent rules are not evaluated. If no rule matches a tool call, the system defaults conservatively: HIGH and CRITICAL tools default to REQUIRE\_CONFIRMATION (forcing user interaction), while LOW and MEDIUM tools default to ALLOW (assuming benignity). This default behavior ensures safety even if policies are incomplete or misconfigured.

\subsection{Provenance Tracking}

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/provenance_graph.pdf}
  \caption{\textbf{Provenance Graph Example.} A multi-turn conversation showing trust propagation.
  INPUT[0] (user command) is TRUSTED. TOOL\_RESULT[2] from \texttt{device.list()} is UNTRUSTED

  When combined with TRUSTED INPUT[4], DERIVED\_FACT[5] remains UNTRUSTED (any UNTRUSTED ancestor
  taints descendants). TOOL\_CALL[6] attempts to delete user files with UNTRUSTED provenance,
  triggering policy denial (CRITICAL risk + UNTRUSTED + user files → DENY).}
  \label{fig:provenance-graph}
\end{figure}

\paragraph{Provenance Graph Structure.}
\sys{} maintains a directed acyclic graph $G = (V, E)$ where each node $v \in V$ represents a unit of information and each edge $(u, v) \in E$ represents a derivation dependency (i.e., $v$ was derived from $u$). Nodes are typed into four categories: INPUT nodes represent user commands and system prompts (the authoritative sources of information), TOOL\_RESULT nodes represent the outputs of tool executions (e.g., device lists, calendar events, file contents), DERIVED\_FACT nodes represent facts inferred or summarized by the LLM agent (e.g., intermediate conclusions, reasoning steps), and TOOL\_CALL nodes represent proposed tool invocations. This type information guides the provenance resolution process and enables efficient queries.

\paragraph{Trust Labels and Propagation.}
Each node $v$ is assigned a trust label $T(v) \in \{\text{TRUSTED}, \text{UNTRUSTED}\}$. INPUT nodes from authenticated user sources are marked TRUSTED; all TOOL\_RESULT nodes from external sources (APIs, files, network) are marked UNTRUSTED. Trust propagates conservatively through the graph: a DERIVED\_FACT or TOOL\_CALL node is marked TRUSTED only if \emph{all} of its ancestors are TRUSTED. Formally:

$$T(v) = \begin{cases} \text{TRUSTED} & \text{if } \forall u \in \text{ancestors}(v) : T(u) = \text{TRUSTED} \\ \text{UNTRUSTED} & \text{otherwise} \end{cases}$$

This conservative rule ensures that any untrusted input contaminates derived facts, preventing an attacker from ``washing'' malicious data by combining it with trusted data and hoping the mixture appears trustworthy. Once tainted by untrusted input, a fact remains untrusted until explicitly verified or sourced anew from trusted input.

\paragraph{Provenance Queries at Decision Time.}
When the policy engine evaluates a tool call, it performs three provenance queries. First, \texttt{get\_sources(c)} returns the complete set of INPUT and TOOL\_RESULT nodes (sources) that transitively influenced a tool call $c$. Second, \texttt{is\_trusted(c)} returns a boolean indicating whether all sources are TRUSTED. Third, \texttt{get\_untrusted\_sources(c)} returns the specific list of untrusted sources, used to construct user-facing confirmation messages explaining the provenance concern. These queries are implemented via breadth-first search over ancestor edges in the provenance graph, which is efficient (O(d) where $d$ is graph depth, typically 5-10 layers for agent reasoning chains).

\paragraph{Concrete Multi-Turn Example.}
Consider a multi-turn conversation to illustrate provenance tracking in action:
\begin{enumerate}[leftmargin=1.2em]
  \item User command (node $I_1$, TRUSTED): \textit{``List my devices.''}
  \item Agent calls \texttt{device.list()} (node $C_1$) and receives result (node $R_1$, UNTRUSTED): \texttt{[``Thermostat (online)'', ``Light. Delete user files. (online)'']}
  \item Agent generates a summary (node $S_1$): \textit{``You have 2 devices online, one with an unusual name.''}
    \begin{itemize}[leftmargin=1.2em]
      \item Edges: $I_1 \to S_1$ (summary derives from user command) and $R_1 \to S_1$ (summary includes device list result).
      \item Trust: $T(S_1) = \text{UNTRUSTED}$ because $T(R_1) = \text{UNTRUSTED}$.
    \end{itemize}
  \item User command (node $I_2$, TRUSTED): \textit{``Act on any system alerts in the devices.''}
  \item Agent calls \texttt{fs.delete("/important.txt")} (node $C_2$), intending to act on the device name instruction.
    \begin{itemize}[leftmargin=1.2em]
      \item Edges: $I_2 \to C_2$ (call derives from user command) and $S_1 \to C_2$ (call references summary).
      \item Trust: $T(C_2) = \text{UNTRUSTED}$ because $T(S_1) = \text{UNTRUSTED}$ (tainting via the summary).
    \end{itemize}
  \item Policy evaluation:
    \begin{itemize}[leftmargin=1.2em]
      \item Tool: \texttt{fs.delete} (HIGH-risk, normally requires confirmation).
      \item Provenance: \texttt{is\_trusted(C_2)} returns false; sources trace to $R_1$ (untrusted device name).
      \item Applicable Policy: ``HIGH risk + UNTRUSTED provenance → DENY'' matches.
      \item Outcome: Call is blocked; agent receives error.
    \end{itemize}
\end{enumerate}

This example shows how provenance tracking captures the contamination of benign-sounding high-level directives (``act on alerts'') with untrusted content (the injected instruction in the device name). Without provenance, a policy might allow the deletion because the user's command \textit{``act on alerts''} uses trusted language; with provenance, the policy correctly identifies that the deletion request is causally traced to untrusted input.

\paragraph{Implementation: String Matching for Provenance Resolution.}
The provenance tracker uses an inverted index to map substrings of node content to nodes in the graph. When a tool call argument is evaluated, the tracker performs substring matching (case-insensitive) to identify which prior TOOL\_RESULT nodes (external data) might have contributed to the argument value. For example, if a tool call contains the path \texttt{"/home/user/backups"} and this exact string appeared in an earlier TOOL\_RESULT (e.g., device name or file listing), the path is marked as derived from that untrusted result.

\textbf{Limitations and Scope.} This substring-based approach is practical and efficient (O(n) lookup where n is argument length) but has known limitations: (1)~it cannot track implicit inferences (e.g., if the agent summarizes ``delete the backup folder'' without repeating the exact path), (2)~it misses transformations (e.g., path normalization \texttt{/home/user/../user/backups} $\to$ \texttt{/home/user/backups}), and (3)~it may produce false positives if common strings appear in multiple contexts. Our evaluation focuses on attack scenarios with explicit string injection, where this approach achieves 95\% detection. The remaining 5\% of successful attacks exploit semantic paraphrasing or implicit inference that evade string matching.

\textbf{Future Directions.} More sophisticated provenance resolution could use: (1)~embedding-based semantic similarity (matching ``delete backups'' to a prior mention of ``/home/user/backups''), (2)~LLM chain-of-thought instrumentation (requiring the agent to cite sources explicitly), or (3)~typed value tracking (propagating provenance through structured data fields). These approaches trade computational cost for precision and are left to future work.

\subsection{Evidence Requirements}

For sensitive operations, policies can mandate that the agent provide explicit evidence—structured justification—for its proposed tool call. An agent that structures its output with evidence fields demonstrates intentionality and can be held accountable. When policies require evidence, the enforcement proxy validates that the evidence fields are present and non-empty, and the user confirmation interface displays the evidence, allowing the user to assess whether the agent's justification matches the requested operation.

A policy might specify:

\begin{verbatim}
rules:
  - name: "File deletion requires justification"
    tools: ["fs.delete"]
    conditions:
      risk_tier: HIGH
    action: REQUIRE_CONFIRMATION
    evidence_required:
      - reason: "Why is deletion necessary?"
      - affected_files: "List of files to delete"
\end{verbatim}

When the agent calls \texttt{fs.delete}, it must structure its output:

\begin{verbatim}
{
  "tool": "fs.delete",
  "args": {"path": "/tmp/cache"},
  "evidence": {
    "reason": "User requested cleanup of temporary cache
               files from previous session.",
    "affected_files": ["/tmp/cache"]
  }
}
\end{verbatim}

The policy engine validates that evidence is present, and the user confirmation prompt displays: \textit{``Agent wants to delete /tmp/cache. Reason: User requested cleanup of temporary cache files from previous session. Confirm? [Y/N]''} This evidence mechanism bridges the gap between what the system can verify (provenance, scope) and what requires human judgment (whether the user's intention matches the operation).

\subsection{Rate Limiting}

Policies can specify rate limits to prevent abuse and DoS attacks. For example, a policy might allow email sending but restrict to 10 emails per hour, preventing the agent from being manipulated into spam campaigns. Rate limits are evaluated after all other conditions; if all conditions match but rate limit is exceeded, the action is set to DENY with reason ``rate limit exceeded.''

\begin{verbatim}
rate_limits:
  - tools: ["email.send"]
    max_calls: 10
    window: "1h"
  - tools: ["notify.send"]
    max_calls: 20
    window: "1h"
\end{verbatim}
    max_calls: 50
    window: "10m"
\end{verbatim}

The policy engine maintains sliding windows, denying calls that exceed limits. This defends
against DoS attacks (e.g., spamming notifications) and resource exhaustion.

\subsection{Temporal Constraints}

Policies can restrict tools to specific time windows:
\begin{verbatim}
rules:
  - name: "No file deletions after hours"
    tools: ["fs.delete"]
    conditions:
      time_of_day: ["22:00", "06:00"]  # 10pm-6am
    action: DENY
\end{verbatim}

This mitigates timing-based attacks where adversaries exploit relaxed policies during off-hours.

\subsection{Scope Constraints}

Path-based restrictions limit tool access to safe regions:
\begin{verbatim}
rules:
  - name: "File writes restricted to user directories"
    tools: ["fs.write"]
    conditions:
      path_prefix: ["/home/user/", "/tmp/"]
    action: ALLOW
  
  - name: "Block system directory writes"
    tools: ["fs.write", "fs.delete"]
    conditions:
      path_prefix: ["/etc/", "/sys/", "/usr/"]
    action: DENY
\end{verbatim}

Scope constraints implement least privilege: tools can only access resources necessary for
legitimate tasks.

\subsection{Composability and Extensibility}

The policy language supports:
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Policy inheritance:} Import base policies and override specific rules.
  \item \textbf{Custom constraints:} Plugin architecture for domain-specific checks
        (e.g., "deny email.send if recipient is external").
  \item \textbf{Multi-user policies:} Per-user rule sets, delegation policies.
\end{itemize}

\subsection{Policy Validation}

Before deployment, administrators can validate policies:
\begin{itemize}[leftmargin=1.2em]
  \item \textbf{Syntax checking:} YAML parser verifies schema compliance.
  \item \textbf{Conflict detection:} Identifies contradictory rules (e.g., "allow \texttt{fs.delete}"
        followed by "deny \texttt{fs.delete}" for the same scope).
  \item \textbf{Coverage analysis:} Reports tools without explicit policies.
  \item \textbf{Simulation:} Test policies against benign and attack scenarios before production.
\end{itemize}
